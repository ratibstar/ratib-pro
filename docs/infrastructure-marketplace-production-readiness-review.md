# Infrastructure Marketplace + Control Plane — Production Readiness Review (Audit)

**نوع المستند:** مراجعة جاهزية الإنتاج (Production Readiness Review) — ليس خطة ميزات.  
**النطاق:** `modules/infrastructure-marketplace` + `api/infrastructure-marketplace` + تكامل لوحة التحكم + نظام runtime config.  
**الافتراض:** نشر ليلي على بيئة حقيقية مع مستخدمين ومدراء وطلبات متزامنة وضغط على الويب سيرفر وقاعدة البيانات.

**الخلاصة التنفيذية:** النظام **غير جاهز بالكامل للإنتاج** من منظور أمني وتشغيلي حتى تُغلق ثغرات **Critical** المذكورة أدناه (خصوصًا حماية واجهات الـ API الحساسة ومسارات الجلسة). أجزاء من الطبقة (مرونة `dashboard`، كتابة runtime ذرّية، CSRF على `control-update`) تقلل المخاطر لكنها **لا تعوّض** غياب الحماية الموحّدة على بقية الـ endpoints.

---

## 1) Critical Production Risks (يجب إصلاحها قبل الإنتاج)

### C1 — واجهات API تشغيلية بدون مصادقة موحّدة (أخطر نقطة)

**الوصف:** عدة ملفات تحت `api/infrastructure-marketplace/*.php` تقبل `POST` (أو عمليات حساسة) **دون** ربط إلزامي بجلسة لوحة التحكم أو توكن خدمة. مثال من الكود الحالي: `order.php` و `ops-retry-job.php` يستدعيان المنطق مباشرة بعد `bootstrap` فقط.

**لماذا يهم:** أي طرف يعرف المسار يمكنه استدعاء واجهات الطلب / إعادة الطابور / تفعيل مزود / إلخ حسب ما يعرضه كل ملف — هذا **خرق أمني production** وليس مجرد “نقص ميزة”.

**الأثر إن تجاهل:** تلاعب بطلبات provisioning، إعادة جدولة وظائف، استهلاك موارد، تلويث بيانات، أو مسار هجوم لاحق على المزودين.

---

### C2 — تصعيد صلاحيات عبر `view_control_system_settings` على `control-update.php`

**الوصف:** التحقق من الصلاحية يتضمن `hasControlPermission('view_control_system_settings')` ضمن شرط السماح بالكتابة على runtime config. المستخدم ذو صلاحية **عرض فقط** قد يُعتبر مخولًا بتعديل إعدادات حرجة (`enabled`, `kill_switch`, إلخ).

**لماذا يهم:** مخالفة مبدأ أقل الصلاحيات (Least privilege) — خطأ تصميم أمني مباشر.

**الأثر إن تجاهل:** مستخدم “قراءة فقط” يغيّر سلوك المنصة أو يوقف الخدمة.

---

### C3 — تعارض جلسة PHP بين لوحة التحكم وواجهة `control-update.php` / CSRF

**الوصف:** `control-update.php` يعتمد على `$_SESSION` + `infra_control_csrf_token`. التوكن يُنشأ في `Views/admin/control.php` عبر `session_start()`. لوحة التحكم قد تستخدم **اسم جلسة / مسار كوكي / domain** مختلفًا عن طلب API المباشر إلى `/api/...`، أو قد لا تُحمّل نفس `$_SESSION` في سياق مختلف (iframe، نطاق فرعي، proxy).

**لماذا يهم:** إما فشل دائم للحفظ (419) في الإنتاج، أو في سيناريوهات أسوأ اختلاف سلوك بين البيئات دون اكتشاف مبكر.

**الأثر إن تجاهل:** “زر الحفظ لا يعمل” في الإنتاج، أو فريق يضعف الحماية كحل سريع.

---

### C4 — `ModuleConfig::runtimeOverridesCache` ثابت داخل طلب PHP طويل / worker

**الوصف:** `ModuleConfig` يخزّن نتيجة قراءة `runtime-overrides.json` في `static $runtimeOverridesCache`. بعد تحديث الملف من نفس العملية أو من عملية أخرى، **لا يُعاد تحميل الملف** تلقائيًا داخل نفس عملية PHP طويلة العمر (مثلاً worker أو بعض setups).

**لماذا يهم:** تغيير runtime عبر الملف لا ينعكس فورًا على كل المستهلكين — سلوك غير متوقع تحت الضغط أو بعد kill-switch.

**الأثر إن تجاهل:** فترات تشغيل بإعدادات قديمة بعد “تم الحفظ”، أو قرارات أمان متأخرة.

---

## 2) High Risk Issues

### H1 — سجل التدقيق JSONL على القرص: فشل صامت + تعرض محتمل

**الوصف:** `RuntimeConfigAuditLogger::append()` يتجاهل فشل الكتابة بصمت (`return` بدون إشارة للمستدعي). الملف تحت `modules/.../Audit/` قد يكون **قابلًا للوصول عبر الويب** إذا لم تُقيّد قواعد الخادم.

**لماذا يهم:** فقدان أدلة compliance، أو تسريب من يغيّر ماذا ومتى.

**الأثر إن تجاهل:** اعتقاد خاطئ بأن كل تغيير مسجّل؛ أو تسريب بيانات تشغيلية.

---

### H2 — `control-update.php`: مسار `tenant_allowlist` عبر JSON body

**الوصف:** المعالجة الحالية تفترض غالبًا سلسلة نصية مفصولة بفواصل. إذا أرسل العميل JSON بمصفوفة (`tenant_allowlist: [1,2,3]`)، تحويل PHP لسلسلة قد ينتج سلوكًا غير مقصود (مثل `"Array"` كنص).

**لماذا يهم:** بيانات rollout خاطئة دون خطأ واضح للمستخدم.

**الأثر إن تجاهل:** allowlist فارغ أو غير صحيح — توسيع/تقييد خاطئ للنطاق.

---

### H3 — كتابة `runtime-overrides.json` عبر `unlink` ثم `rename` (منصات / NTFS)

**الوصف:** `RuntimeOverrideStore` يحذف الملف الحالي عند فشل `rename` الأول ثم يعيد المحاولة. على بعض أنظمة الملفات أو أذونات Windows قد يكون هناك نافذة ضيقة أو race مع قارئ آخر.

**لماذا يهم:** احتمال نادر لكنه حقيقي لـ “ملف مفقود لحظيًا” أو خطأ I/O.

**الأثر إن تجاهل:** قراءات فارغة مؤقتة، أو فشل تشغيل حتى يُعاد إنشاء الملف.

---

### H4 — عدم وجود versioning رسمي للـ runtime config

**الوصف:** الملف الواحد `runtime-overrides.json` هو المصدر؛ لا يوجد نسخ تلقائية مرقمة (v1, v2) أو hash للتحقق من التكامل.

**لماذا يهم:** التراجع اليدوي صعب تحت الضغط.

**الأثر إن تجاهل:** وقت استرداد أطول، أخطاء بشرية عند التراجع.

---

### H5 — `dashboard.php` كمجمع كبير لبيانات متعددة

**الوصف:** نقطة واحدة تجمع DB + مزودين + أوامر + تدقيق. حتى مع `try/catch` جزئي، أي خطأ غير متوقع في طبقة جديدة قد يزيد التعقيد.

**لماذا يهم:** نقطة مركزية للمراقبة لكنها أيضًا نقطة **تجمّع فشل** من ناحية التشغيل والصيانة.

**الأثر إن تجاهل:** صعوبة تشخيص، timeouts على طلبات HTTP طويلة إذا توسّع الاستعلام.

---

## 3) Security Gaps (حتى مع CSRF + RBAC الجزئي)

### S1 — Bypass عبر endpoints أخرى غير محمية (مرتبط بـ C1)

**الوصف:** الحماية موجودة على `control-update.php` لكن ليس بالضرورة على `order.php`, `lifecycle-action.php`, `provider-activation.php`, `ops-*.php`, إلخ.

**لماذا يهم:** المهاجم لا يحتاج لتجاوز CSRF إذا كان المسار مفتوحًا.

**الأثر:** خرق كامل لطبقة “Control Plane” المفترضة.

---

### S2 — CSRF لا يمنع طلبًا من مستخدم شرعي مسروق الجلسة

**الوصف:** CSRF يحمي من مواقع خارجية، لا يحمي من XSS داخل نفس الموقع أو جلسة مسروقة.

**لماذا يهم:** يجب تكامل مع `SameSite`, HttpOnly, Secure cookies, ومراقبة XSS.

**الأثر:** تنفيذ إجراءات بحساب مدراء إذا تسربت الجلسة.

---

### S3 — سجل JSONL قابل للتلاعب على مستوى نظام الملفات

**الوصف:** أي من لديه وصول SSH أو كتابة على المجلد يمكنه تعديل/حذف السجل.

**لماذا يهم:** الاعتماد على الملف كمصدر حقيقة وحيد غير كافٍ لـ compliance صارم.

**الأثر:** إنكار التلاعب أو صعوبة إثبات سلسلة الحفظ.

---

### S4 — `REMOTE_ADDR` فقط للممثل في السجل

**الوصف:** خلف `CDN`/`load balancer` قد يكون العنوان غير تمثيلي للعميل الحقيقي دون `X-Forwarded-For` الموثوق.

**لماذا يهم:** سجلات أقل فائدة في التحقيق.

**الأثر:** صعوبة تتبع الحوادث.

---

## 4) Architecture Weak Points

### A1 — تشتيت مصدر الحقيقة للتفويض (AuthZ)

**الوصف:** جزء من الـ API يعتمد على “عامة + bootstrap” وجزء على لوحة التحكم — لا يوجد middleware موحّد واضح لكل `api/infrastructure-marketplace/*`.

**لماذا يهم:** كل ملف جديد يزيد خطر نسيان الحماية.

**الأثر:** ثغرات متكررة بنفس النمط.

---

### A2 — `ModuleConfig` يدمج env + ملف JSON بدون طبقة “schema” مركزية

**الوصف:** المفاتيح موزعة على getters؛ التحقق من الأنواع في `control-update` منفصل عن قراءة `ModuleConfig`.

**لماذا يهم:** احتمال انحراف بين “ما يُكتب” و“ما يُقرأ” عند إضافة مفتاح جديد.

**الأثر:** أخطاء صامتة أو قيم تُتجاهل.

---

### A3 — “God endpoint” نسبيًا: `dashboard.php`

**الوصف:** يجمع صحة، طابور، مزودين، أوامر، تدقيق في استجابة واحدة.

**لماذا يهم:** صعب الحد من الصلاحيات per-endpoint، وصعب caching آمن، ويزيد زمن الاستجابة.

**الأثر:** timeouts، تكلفة DB أعلى تحت الحمل.

---

## 5) Observability Gaps

### O1 — فشل التدقيق صامت

**الوصف:** لا يوجد counter أو log بديل عند فشل `RuntimeConfigAuditLogger`.

**لماذا يهم:** مراقبة خاطئة — “التغيير نجح” لكن السجل لم يُكتب.

**الأثر:** فجوات في التحقيق بعد الحوادث.

---

### O2 — لا يوجد معيار موحّد لـ SLO على `control-update`

**الوصف:** لا توجد metrics صريحة (latency, rate limit hits, 403/419 counts) في هذا المسار ضمن التقرير الحالي للكود.

**لماذا يهم:** صعوبة اكتشاف هجمات brute أو أخطاء تكامل.

**الأثر:** اكتشاف متأخر للحوادث.

---

### O3 — `dashboard` يعتمد على structured logging قد يفشل خارجيًا

**الوصف:** تم تقليل احتمالية كسر الاستجابة سابقًا، لكن الاعتماد على emitter خارجي للملاحظات الكاملة قد يبقى غير متسق بين البيئات.

**الأثر:** لوحات مراقبة ناقصة دون أن يعلم المشغّل.

---

## 6) Operational Gaps

### OP1 — لا rollback آلية للـ runtime file

**الوصف:** التراجع يعتمد على نسخ يدوية أو git على السيرفر — ليس جزءًا من مسار API.

**الأثر:** وقت استرداد أطول تحت الضغط.

---

### OP2 — تلف `runtime-overrides.json` يدويًا

**الوصف:** `ModuleConfig` يعامل JSON غير صالح كـ `[]` فعليًا (مصفوفة فارغة) بعد فشل decode — قد يبدو “العودة للافتراضي” دون إنذار واضح في كل مسار.

**الأثر:** سلوك يشبه “تعطيل الـ overrides” دون قصد.

---

### OP3 — عدم وجود حد معدل (rate limit) على `control-update`

**الوصف:** مستخدم أو سكربت خاطئ قد يرسل طلبات متكررة — القفل يمنع corruption لكن لا يمنع الضغط.

**الأثر:** I/O مرتفع، إرهاق القرص، log ضخم.

---

## 7) Edge Cases Not Handled (أو غير مكتملة)

| الحالة | المخاطرة |
|--------|-----------|
| تحديثان متزامنان لـ runtime من مديرين | آخر كاتب يفوز؛ لا يوجد optimistic locking / revision |
| JSON body لـ `tenant_allowlist` كمصفوفة | خطأ منطقي محتمل في القيم |
| جلسة منتهية أثناء إرسال النموذج | 403/419 — يحتاج UX واضح + تجديد توكن |
| فشل القرص ممتلئ أثناء atomic write | خطأ 500 — جيد، لكن بدون تنبيه تشغيلي مركزي |
| قراءة `runtime-overrides.json` أثناء rename | نادر؛ القفل يقلل لكن القراءة خارج القفل في `read()` عند عدم القفل |

## تصنيف المخاطر (ملخص تنفيذي)

### Critical (must fix before production)
- **C1:** APIs حساسة بدون مصادقة/تفويض موحّد.
- **C2:** كتابة runtime لمن لديه صلاحية عرض فقط.
- **C3:** مخاطر جلسة/CSRF عبر السياقات الفرعية والـ iframe.
- **C4:** كاش ثابت لـ runtime overrides داخل العملية.

### High Risk
- **H1–H5:** تدقيق صامت، parsing allowlist، I/O rename، عدم versioning، تعقيد `dashboard`.

### Medium Risk
- **S2–S4:** حدود CSRF، سجل قابل للتلاعب على FS، عناوين IP خلف CDN.
- **A1–A3:** تشتيت AuthZ، عدم schema مركزي، god endpoint.
- **OP2–OP3:** تلف JSON، عدم rate limit.

### Minor Issues
- اختلاف تنسيق الأخطاء في بعض المسارات (405 خارج `$respond` الموحّد في `control-update` للـ method غير POST — مسار نادر).
- توثيق تشغيلي للمشغّلين حول: أذونات الملفات، منع الويب من قراءة `Audit/*.jsonl`, ومسار الجلسة.

## الحكم النهائي: هل النظام Production-ready؟

**لا — ليس بالمعنى الأمني والتشغيلي الكامل للإنتاج العام** حتى تُغلق على الأقل:

1. حماية **جميع** واجهات `api/infrastructure-marketplace` الحساسة (مصادقة + تفويض + معدل طلبات حيث يلزم)، وليس `control-update` فقط.  
2. تقييد كتابة runtime على **صلاحية تعديل صريحة** (مثل `edit_control_system_settings` أو صلاحية مخصصة)، وليس `view_*`.  
3. معالجة **تجديد/توحيد الجلسة** بين لوحة التحكم ومسار API (أو نقل التحديث إلى `control-panel/api/...` بنفس جلسة اللوحة).  
4. إصلاح **كاش `ModuleConfig`** بعد تغيير الملف (إعادة تحميل أو TTL أو `clearstatcache` + إبطال كاش عند الكتابة).

بعد إغلاق النقاط أعلاه يمكن اعتبار المنظومة **أقرب بكثير** إلى جاهزية الإنتاج، مع بقاء تحسينات مراقبة ونسخ احتياطي للـ runtime كعمل تشغيلي مستمر.
